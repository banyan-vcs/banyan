# 11 · 高可用与集群部署

## 0. 决策变更记录

docs/02 §2 风险表曾把元数据服务的生产接替路径列为"分布式 SQL（TiDB/CockroachDB）
或 MySQL + 单写者"。本设计改为**内嵌 Raft 复制组**：

- 不引入外部数据库依赖——"单二进制 + SQLite 起步，按需生长到集群"的定位要求
  HA 形态自包含；
- MetaStore 的写面本来就是低频命令流（每 push 一条 PutPack + 一条 CASHead），
  Raft 日志量与业务量同阶，无写放大问题；
- CAS 语义（expected/next）在 FSM apply 端天然确定性重放，不需要 SQL 事务的
  表达力。

外置 SQL 降级为"元数据审计/报表的旁路读"远期选项，不再是 HA 主路径。

## 1. 目标与非目标

**目标**：

1. **一体化部署**：单进程单命令跑起完整服务（现状形态，零额外配置）；
2. **集群化部署**：同一二进制拆分为**服务网关**与**存储集群**两类角色；
3. 集群采用 **Raft** 复制元数据；仓库数据（pack）按**仓库级副本数 R** 复制，
   R 动态可调（1..N）；
4. R≥3 平稳高可用（单节点故障不影响读写且仍满足副本目标）；兼容 R=1/2；
5. git 客户端、薄 CLI、未来 Gitaly 前端对部署形态**完全无感**。

**非目标**：跨机房容灾（远期：异步跨集群复制）；多主写（CP 系统，单 leader）；
元数据外置数据库部署形态。

## 2. 部署形态：同一二进制，角色切换

```
一体化（all-in-one，默认）：
  banyand ── 网关 + 单成员 raft 组 + 本地 shard
  （现状即此形态；raft 组退化为 1 成员，代码路径与集群完全一致——
    单机不是特例分支，这是本设计的第一原则）

集群化（cluster）：
  ┌────────── 服务网关层（无状态，横向扩，前置 LB 由环境自备）──────────┐
  │  git smart HTTP / JSON API /（规划）Gitaly 前端                        │
  │  鉴权（M5 token 挂点）/ 限流 / TLS 终止                                │
  │  视图引擎（织入）+ pack cache + 视图缓存（确定性纯函数 ⇒ 副本间一致）    │
  └──────────┬─────────────────── 元数据 RPC ───────────────────────────┘
             ▼
  ┌── 存储集群（raft 组，推荐 3/5 成员，奇数）──────────────────────────┐
  │  node-1   raft voter + FSM(SQLite) + shard store                     │
  │  node-2   raft voter + FSM(SQLite) + shard store                     │
  │  node-3   raft voter + FSM(SQLite) + shard store                     │
  └─────────────────────────────────────────────────────────────────────┘
```

- `banyand -role gateway -gateway.cluster node-1:8102,...`
- `banyand -role node -raft.node-id node-1 -raft.peers ...`
- git smart HTTP v1 每请求自包含（info/refs / upload-pack / receive-pack 各自
  一次 HTTP），**网关无需会话粘滞**，可任意扩展与故障转移；
- 网关持有缓存（pack / 解码对象 / 视图）但无权威状态——任何网关可随时增删。

## 3. 控制面与数据面分离

| 面 | 内容 | 复制方式 | 一致性 |
|---|---|---|---|
| **控制面**（元数据） | repos / timelines（head CAS）/ packs 注册 / objects 定位表 / placement | **Raft 日志复制**，FSM = 命令确定性重放，快照 = SQLite | 线性化（写走 leader apply；读默认走 leader） |
| **数据面**（pack 字节） | pack + idx 文件 | **不经 raft**：网关直连目标节点并行流式写入 | 不可变内容寻址 ⇒ 无序复制安全；"先落盘后提交元数据"保证读己之写 |

pack 字节不走 raft 日志的原因：体积大（单 pack 可达数百 MB）且不可变——
复制不需要日志定序，只需要"至少一份数据先于元数据提交持久化"。

## 4. 元数据面：Raft

**命令集**（FSM Apply 输入，与 MetaStore 写方法一一对应）：

```
CreateRepo{repo, algo}                      PutPack{repo, packOID, objects[], nodes[]}
CASHead{timeline, expected, next}           EnsureTimeline{timeline, head, base}
DropPack{repo, packOID}                     UpdatePlacement{repo, replicas}
```

每条命令是全序日志中的一个 entry；FSM 在每个节点确定性重放到本地 SQLite。
CAS 的 expected 校验发生在 apply 端（所有节点同一结果），leader 无需预检。

**读写语义**：

- 写：网关（或集群节点自身）把命令发给 raft leader，等待 commit+apply 后返回；
- 读：v1 一律由 leader 服务（非 leader 节点代理转发）；性能优化路径为
  leader-lease 读（follower 确认 leader 存活期间本地 FSM 直接服务，免转发）；
- 崩溃窗口：PutPack 与 CASHead 是两条命令，中间崩溃留下孤儿 pack——无害
  （未被任何 head 引用），reconciler 兜底回收，语义与单机 repack 崩溃窗口同构。

**成员管理**：新增节点以 learner（非投票成员）加入，日志追平后提升 voter；
移除节点先降级 learner 再摘除；成员变更本身走 raft 配置条目。推荐 3 成员起步
（容忍 1 故障），5 成员容忍 2。

## 5. 数据面：pack 复制与写路径

**push 写路径**（网关执行）：

```
① 解码 pack → 计算 packOID
② 放置：PickNodes(目标 R, 排除不健康节点)（rendezvous，docs/02 §1.2）
③ 并行流式写 pack+idx 到各目标节点（同步等待；超时/失败者剔除）
   → 得到确认集 C（|C| ≥ 1，否则 503 拒绝）
④ raft apply PutPack{objects, nodes: C}     ← 元数据只登记已确认节点
⑤ raft apply CASHead                        ← 唯一串行点，语义与单机完全一致
```

读己之写由顺序保证：元数据提交时数据已在 C 个节点持久化。目标 R 未凑齐时
**降级成功**（C < R），reconciler 异步补齐——可用性优先于副本目标。

**读路径**：objects 定位表给出 (packOID, nodes[])，按序尝试，网关本地 cache
短路；整 pack 直传（ExactPackHit）语义保持——直接从任一持有节点流式回传。

## 6. 仓库级副本数：动态调整

- 每仓库一条 placement 记录：`repo → target R`（默认取集群配置
  `placement.default_replicas`，建仓时落定，随时可改）；
- API：`PUT /api/v1/repos/<repo>/placement {"replicas": R}` → raft apply；
- **reconciler**（raft leader 上单实例运行，leader 漂移则随之漂移）持续对账
  `pack_nodes` 与目标 R：
  - 欠副本（含节点下线/移除导致的缺失）：选新节点 → 节点间直连复制 pack →
    raft apply 更新 pack_nodes → 达标；
  - 超副本（R 下调 / 节点加入重平衡）：先在别处确认达标，再从多余节点删除；
  - 孤儿 pack 回收（无 objects 行指向且无引用）；
  - 不可变数据使以上操作**无锁安全**：复制与删除都是幂等 CAS，随时可中断重跑。
- 收敛为渐进式（有界并发 worker），大仓扩副本不阻塞前台读写。

## 7. 可用性语义（N = 集群投票成员数，R = 仓库副本数）

两个独立的轴，分开陈述：

| N（元数据面） | 容错 | 说明 |
|---|---|---|
| 1 | 0 | 一体化/单机 |
| 2 | 0 | 可部署；单节点故障期间**不可写**（CP；raft quorum=2），数据不丢，恢复即续 |
| 3 | 1 | HA 推荐最小配置 |
| 5 | 2 | |

| R（数据面） | 单节点故障时 |
|---|---|
| 1 | 仓库数据不可用（无冗余；适合冷仓/开发仓） |
| 2 | **可读**，且可从幸存副本补齐 |
| ≥3 | **可读可写**且仍满足副本目标（平稳 HA） |

R ≤ N 恒成立；per-repo 取值使存储成本与重要性对齐（核心仓 R=3，边缘仓 R=1）。
降级读开关（quorum 丢失时允许本地 FSM 陈旧读）默认关闭，显式配置才启用。

## 8. 故障场景与恢复

| 故障 | 影响 | 恢复 |
|---|---|---|
| 网关实例宕 | 无感（LB 摘除）；进行中 HTTP 请求客户端重试 | 无需恢复动作 |
| raft leader 宕 | 写短暂不可用（选举 ~1s）；进行中 push 客户端侧失败 | 选举完成即续；重试幂等（pack CAS + CASHead expected） |
| 集群节点宕（非 leader） | R≥2 仓库可读可写；欠副本进入对账队列 | 节点回归：raft 追日志（落后多则快照），reconciler 只补缺失 pack |
| 双节点同时宕（3 成员集群） | 元数据不可用（quorum 丢失）；数据不丢 | 任一节点回归即恢复 quorum |
| 磁盘损坏单节点 | 该节点数据丢失 | 节点重建（清空加入），reconciler 从他副本全量回填 |

## 9. 配置形态（banyan.yaml）

```yaml
role: node                      # all-in-one（默认）| gateway | node
listen: 0.0.0.0:8080
root: /var/lib/banyan           # shard 数据（node/all-in-one）
raft:                           # role=node / all-in-one
  node_id: node-1
  peers: ["node-1@h1:8101", "node-2@h2:8101", "node-3@h3:8101"]  # 初始成员，此后由 raft 管理
  data_dir: /var/lib/banyan/raft
placement:
  default_replicas: 2
gateway:                        # role=gateway
  cluster: ["h1:8102", "h2:8102", "h3:8102"]   # 集群服务端点
```

节点间内部端口（raft 8101 / 数据服务 8102）不对外暴露；节点互信 v1 用共享
token（随 M5 认证体系升级为 mTLS）。

## 10. 与现有代码的映射

| 现有构件 | 集群化后的去处 |
|---|---|
| `MetaStore` 接口 | 不变；新增 `RaftMetaStore` 实现（写转发 leader，读 leader/lease）；FSM 复用 sqlite 后端的表结构 |
| `ObjectService.Node`（Local 标记 + TODO(M2) 远端取） | 远端 shard RPC 落地即此 TODO；网关持有节点客户端池 |
| `PickNodes` rendezvous | 保留，输入从"全部节点"变为"健康节点 ∩ 目标 R" |
| `rpc/gitwire/service` 三层 | 整体成为网关角色；Gitaly 前端（docs/10）同样挂在网关 |
| 一体化部署 | = 单成员 raft 组 + 本地 shard；**无特例代码路径** |
| repack（register-first） | leader 单飞编排（follower 收到的就是 PutPack/DropPack 命令流），协议不变 |

## 12. 里程碑与风险

```
HA-1：RaftMetaStore + 角色（gateway/node）+ 节点间数据 RPC + per-repo placement + reconciler
HA-2：成员运维（learner 加入/提升/移除）、快照与备份、leader-lease 读
HA-3：机架/可用区感知放置、跨集群异步复制（容灾）
```

roadmap 对位：HA-1 吸收原 M2 的"ShardStore 远端 + rendezvous + R 副本"三项。

| 风险 | 缓解 |
|---|---|
| raft 日志重放对 sqlite FSM 的压力 | 命令低频（每 push 2 条）；快照定期截断日志 |
| 大 pack 并行写的网关带宽 | 数据面不经网关的备选：节点间直连复制（reconciler 已是；写路径 v2 演进） |
| 网关视图缓存一致性 | 视图是 (tips) 的确定性纯函数，缓存键含 tips 代次；陈旧读最坏导致一次多余的 head 复核 |
| hashicorp/raft 依赖引入 | 单一成熟库（consul/nomad 同源）；MetaStore 接口隔离，可替换自研 |
