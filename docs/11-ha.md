# 11 · 高可用与集群部署

## 0. 设计沿革（决策记录）

| 版本 | 架构 | 结论 |
|---|---|---|
| v0.1（同日早稿） | raft 复制**元数据**；pack 字节网关直连复制 | 弃用：①元数据 raft 组是全局单选主域，与吞吐目标冲突；②pack 复制无共识语义，副本确认是"尽力而为"；③仓库副本数与 raft 容错脱节（R 语义弱） |
| **v0.2（本稿，用户定调）** | **元数据与对象存储分离；raft 体现在 pack 存储层** | 元数据回归 docs/02 原生的轻量单写者形态；pack 复制获得完整共识语义（quorum 提交、组内选主、成员变更），per-repo 副本数 R 直接映射 raft 组容错 |

分离的吞吐含义：pack 大流量（单包可达数百 MB）完全不经过元数据路径；元数据
只处理行级小事务，延迟稳定在毫秒级；两类组件按各自负载独立扩缩。

## 1. 目标与非目标

**目标**：

1. **一体化部署**（默认，现状形态）与**组件化集群**共用同一二进制，角色切换；
2. 集群角色三分：**服务网关**（无状态）/ **元数据服务**（单写者 + 热备 + 只读
   副本）/ **pack 存储集群**（raft 组），各自独立水平扩展；
3. raft 用于 pack 存储层：仓库数据按**仓库级副本数 R** 组成 raft 组复制——
   R≥3 单节点故障**读写皆续**（平稳 HA）；兼容 R=1（无冗余）与 R=2
   （单故障可读、新写阻塞的明确降级语义）；
4. R 在仓库级别**动态可调**；
5. git 客户端 / 薄 CLI /（规划）Gitaly 前端对部署形态完全无感。

**非目标**：跨机房容灾（远期异步复制）；多主写（CP）；元数据外置分布式 SQL
（保持 docs/02 §2 单写者设计不动摇）。

## 2. 组件与部署形态

```
┌─ 服务网关 ×N（无状态，前置 LB 自备）──────────────────────────────┐
│ git smart HTTP / JSON API /（规划）Gitaly 前端 / 鉴权（M5 挂点）     │
│ 视图引擎（织入，确定性纯函数）+ pack cache + 视图缓存                │
└────┬────────────────────────────────┬─────────────────────────────┘
     │ 元数据 RPC（小事务 / 点查）       │ pack 数据 RPC（大流量）
     ▼                                 ▼
┌─ 元数据服务 ──────────┐   ┌─ pack 存储集群（raft 组池）──────────────┐
│ 主：单写者（SQLite/    │   │ pool-R3: 组₁(s₁s₂s₃) 组₂(s₄s₅s₆) …      │
│   MySQL）             │   │ pool-R2: 组₃(s₁s₄)   组₄(s₂s₅) …        │
│ 备：同步热备（WAL 流） │   │ pool-R1: 单成员组（s₆）…                 │
│ 只读副本 ×K（异步）    │   │ 仓库 → 按 R 选池 → rendezvous(packOID) 入组│
└───────────────────────┘   │ 写：组 leader（raft 日志，quorum 持久）    │
                            │ 读：任一成员（committed 不可变）           │
                            └──────────────────────────────────────────┘
```

- `banyand -role gateway|meta|storage|all-in-one(默认)`；
- **一体化** = 三角色同进程：meta 为进程内 SQLite 直调，storage 为每仓单成员
  raft 组——**无特例代码路径**（第一原则，与 v0.1 相同）；
- git smart HTTP v1 每请求自包含 ⇒ 网关无会话粘滞，任意增删；
- **组池模型**：raft 实例数与仓数解耦（集群级组池按 R 分池，同 R 仓库共享；
  超大仓可独占组，G 为吞吐旋钮）。

## 3. pack 存储层：per-repo 副本的 raft 组

**组与放置**：仓库的 R 决定其 pack 落入的组池（pool-R{R}）；组内 R 成员由
放置策略从存储节点中组成（初始轮转，节点加入/离开时组内 raft 成员变更）。
pack 按 rendezvous(packOID) 落入池中某组。

**写**：网关 → 组 leader 提交 PutPack（raft 日志携带 pack 字节）→ 多数派
持久 → commit → ack 返回**已提交成员集 C**。

**读**：任一成员可服务——pack 不可变，"存在 = 已提交 = 多数派成员皆有"，
无需线性化读；读吞吐随成员数线性扩展。

**成员追赶**（混合，Kafka 式）：短滞后走 raft 日志；长滞后/新成员先按
**存量 pack 清单**对比复制（节点间直连流），再尾随日志——快照机制不承载
pack 字节。

**R 动态调整**（reconciler 编排，元数据主上单飞）：

- 扩 R（2→3）：目标池选组（learner 追平存量）→ 数据迁移 → 元数据重注册
  pack 成员集 → 旧池删除；
- 缩 R（3→2）：先在目标池确认，再移除源池副本；
- 偶数 R 提示：raft 多数派下 R=4 容错=R=3，推荐奇数；偶数值允许（平滑
  过渡/成本权衡），语义按多数派陈述。

## 4. 元数据服务（独立组件，轻量单写者）

- **形态**：主（单写者，SQLite 起步 / MySQL 可选）+ **同步热备**（WAL 流
  复制，RPO=0，提升切换秒级）+ **异步只读副本 ×K**（横向扩读）；
- **写**：每 push 一个原子事务 `CommitPush{对象定位行 → (packOID, 成员集C),
  CASHead}`——单命令原子提交，**消除 v0.1 的两命令崩溃窗口**；
- **读**：refs / timeline 走主库强读（广告与 old 值正确性）；对象定位 /
  仓库列表走只读副本，**未命中回主库**（覆盖"push 后立即 fetch"的读己之写
  窗口——副本滞后最多造成一次回主库查询，不产生错误结果）；
- **吞吐边界**：行级小事务（每 push 1 事务），单写者上限即全系统提交吞吐
  上限；按量级估算（亚毫秒事务）远超 git push 到达率，实测不足再升 MySQL。

## 5. 写路径（push）

```
① 网关解码 pack → packOID
② 放置：仓库 R → 组池 → rendezvous(packOID) 选组
③ 网关 → 组 leader：PutPack（raft 日志，多数派持久后 commit）→ 确认集 C
④ 元数据主：事务 CommitPush{objects→(packOID, C), CASHead}
⑤ report-status
```

崩溃窗口：③ 后 ④ 前 → 孤儿 pack（组内存在、元数据无注册）——无害，
reconciler 回收；④ 原子 → 无中间态。读己之写 = 主库强读 + 组内 committed。

## 6. 读路径

refs 广告（主库）→ 闭包与对象定位（只读副本，miss 回主库）→ pack 从组内
**任一成员**流式获取（网关 cache / 整包直传语义保持——直接回传成员持有的
pack 字节）。

## 7. 可用性语义

**元数据面**：主备 RPO=0；主宕 → 备提升（秒级），窗口内不可写（CP）。

**数据面**（per-repo R，raft 多数派）：

| R | 单节点故障时 |
|---|---|
| 1 | 该仓数据不可用（无冗余；冷仓/开发仓） |
| 2 | **已提交数据可读**（幸存者持全量 committed）；**该仓新写阻塞**（quorum=2）；节点回归即恢复 |
| 3 | **读写皆续**（quorum=2）——平稳 HA，仍满足副本目标 |
| 5 | 容忍 2 节点故障 |

组件级故障：

| 故障 | 影响 | 恢复 |
|---|---|---|
| 网关实例宕 | 无感（LB 摘除） | 无动作 |
| 元数据主宕 | 窗口内不可写；已提交事务零丢失（同步热备） | 备提升（秒级） |
| 组 leader 宕 | 该组写 ~1s 阻塞（选举） | 选出即续；进行中 pack 写网关侧重试（raft 日志幂等） |
| 存储节点宕 | 其参与组的 R=3 仓读写皆续；R=2 仓读可用写阻塞；R=1 仓不可用 | 节点回归：存量清单对比补差 + 日志尾随 |
| 组内双成员同时宕 | 该组不可用（quorum 丢失）；数据不丢 | 任一回归即恢复 |

## 8. 配置形态（banyan.yaml）

```yaml
role: all-in-one            # all-in-one（默认）| gateway | meta | storage
listen: 0.0.0.0:8080
root: /var/lib/banyan       # storage 角色：pack 数据
meta:                       # meta 角色
  backend: sqlite           # sqlite | mysql
  standby_of: ""            # 热备填主地址；主留空
  read_replica_of: ""       # 只读副本填主地址
raft:                       # storage 角色
  node_id: s1
  listen: 0.0.0.0:8101
gateway:
  meta: ["m1:8102"]         # 元数据服务端点（主）
  cluster: ["s1:8101", "s2:8101", "s3:8101"]   # 存储节点
placement:
  default_replicas: 3
```

内部端口（raft 8101 / 元数据 8102）不对外；节点互信 v1 共享 token（随 M5
认证升级 mTLS）。

## 9. 与现有代码的映射

| 现有构件 | 集群化后的去处 |
|---|---|
| `MetaStore` 接口 | 不变；集群实现 = 元数据服务客户端（写=CommitPush 事务；读=主/副本路由） |
| `ObjectService.lookupPack`（本地盘） | 改为组成员客户端（任一成员取 pack） |
| `PickNodes` rendezvous | 保留，语义变为"组选择" |
| `rpc/gitwire/service` 三层 | 整体成为网关角色（Gitaly 前端同挂网关） |
| 一体化部署 | meta 进程内直调 + storage 单成员组；无特例路径 |
| repack（register-first） | 网关/元数据主编排：读各组成员包 → 合并包写组（raft）→ 元数据 DropPack + 组内删除命令 |

## 10. 测试计划（docs/07 约定）

| # | 用例 | 防回归点 |
|---|---|---|
| T23 | R=3 组杀 leader：选举 → push 重试成功、数据零丢失 | 组内选主与写恢复 |
| T24 | R=2 组单成员离线：**已提交数据可读**（幸存成员）+ 新写干净拒绝；回归恢复 | 降级语义正确性 |
| T25 | R 2→3 跨池迁移：等收敛后杀一节点，读写皆续 | 动态副本与多数派容错 |
| T26 | 元数据主备切换：已提交事务零丢失（RPO=0）+ 窗口内写拒绝 | 元数据 HA 承诺 |
| T27 | 只读副本滞后下的读己之写：push 后立即 fetch（miss 回主库路径） | 读路由正确性 |
| 单元 | 组 FSM（pack 集合）重放确定性；CommitPush 事务原子性；成员追赶状态机 | raft 语义前提 |

## 11. 里程碑与风险

```
HA-1：三角色拆分 + 元数据主备/只读副本 + per-repo raft 组（组池）+ reconciler
HA-2：组运维（成员变更/节点上下线自动化）、lease 读、备份
HA-3：机架/可用区感知放置、跨集群异步复制（容灾）
```

roadmap 对位：HA-1 吸收原 M2 的"ShardStore 远端 + rendezvous + R 副本"三项。

| 风险 | 缓解 |
|---|---|
| raft 日志携带 pack 字节，大包提交时延升高 | entry 分块（实现期定）或"日志只记元数据 entry + 字节旁路 quorum 写"（语义等价：多数派确认后才 commit entry） |
| 多 raft 实例的资源开销 | 组池模型已与仓数解耦；组实例惰性启停 |
| 元数据单写者吞吐上限 | 行级小事务量级估算充裕；实测不足升 MySQL（接口不变） |
| 只读副本滞后窗口 | miss 回主库兜底（正确性无损，最多一次额外查询） |
| hashicorp/raft 依赖 | 成熟单库（consul/nomad 同源）；MetaStore/Node 接口隔离，可替换 |
