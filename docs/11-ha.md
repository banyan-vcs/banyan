# 11 · 高可用与集群部署

## 0. 设计沿革（决策记录）

| 版本 | 架构 | 结论 |
|---|---|---|
| v0.1（同日早稿） | raft 复制**元数据**；pack 网关直连写副本 | 弃用：元数据 raft 组是全局选主域，吞吐目标下过重；但"pack 无需共识"的方向已浮现 |
| v0.2（同日二稿） | 元数据/存储分离；raft 组承载 **pack 字节** | 弃用：raft 的定序/选主对不可变 CAS 对象没有消费者；字节进日志带来写放大与别扭的追赶机制 |
| **v0.3（本稿，用户模型定稿）** | **packfile 散布存储（随机多副本）；ref 存储与 packfile 存储分离，承载前序判断** | git 协议的唯一串行点是 ref 更新（old/new 前序比对 + FF 判定），只依赖 ref 状态、与 pack 位置无关 ⇒ 字节面零共识机制，散布 + 副本即可；串行点收敛为独立 ref 服务 |

## 1. 核心原理：前序判断与字节存储分离

git push/fetch 协议里只有一处需要**串行化**：

- **push**：`(old, new, ref)` —— 服务端判断 old 是否等于当前 ref 值（CAS /
  前序判断），通过才移动 head；
- **fetch**：ref 广告 = 读当前 ref 状态。

这两件事**只依赖 ref 状态**，与 pack 字节放在哪台服务器无关。其余一切
——packfile——是不可变内容寻址对象：同名即同内容（OID = 校验和）、写一次、
永不修改。因此：

```
ref 存储（branch/tag/时间线 + 对象索引）  ← 串行点：前序判断，小事务
pack 存储（散布 + 多副本）               ← 字节仓库：零共识，随机放置
```

分离的红利：pack 大流量与网络扇出完全不经过串行点；两类组件独立扩缩；
故障域细分到单 pack 写。

## 2. 组件与部署形态

```
┌─ 服务网关 ×N（无状态，前置 LB 自备）─────────────────────────────┐
│ git smart HTTP / JSON API /（规划）Gitaly 前端 / 鉴权（M5 挂点）    │
│ 视图引擎（织入，确定性纯函数）+ pack cache + 定位缓存               │
└────┬──────────────────────────────┬──────────────────────────────┘
     │ ref RPC（小事务 / 前序判断）    │ pack 数据 RPC（大流量）
     ▼                              ▼
┌─ ref 服务（串行点）──────┐   ┌─ pack 存储集群（散布多副本）────────┐
│ refs/timelines CAS       │   │ 节点 s1   s2   s3   s4   s5 …      │
│ 对象索引 oid→(pack,节点)  │   │ 任意 pack 可在任意 R 个节点上        │
│ 仓库/放置记录             │   │ 仓库 = 大量 packfile 的离散集合，    │
│ 后端：MySQL/PG（默认）或  │   │ 无仓库-服务器亲和                  │
│ 内嵌 raft 组（自包含）    │   │ 写：随机选 R 个健康节点并行落盘      │
│ + 异步只读副本 ×K         │   │ 读：任一持有节点                    │
└──────────────────────────┘   └────────────────────────────────────┘
```

- `banyand -role all-in-one(默认) | gateway | refs | storage`；
- **一体化** = 三角色同进程（ref = 进程内 SQLite 直调；storage = 单节点，
  R=1）——无特例代码路径；
- git smart HTTP v1 每请求自包含 ⇒ 网关无会话粘滞，任意增删。

## 3. pack 存储：散布 + 随机多副本

**放置**：每个 packfile 是独立放置单元。写入时从**健康节点表中随机（或取
最低负载）选 R 个**——仓库与服务器无亲和，天然均衡；pack 的实际持有集记录在
ref 服务的对象索引中，**读不依赖任何放置函数**（登记即事实）。

**写**（push 路径中段）：

```
网关并行流式写 R 个目标节点（pack+idx，内容寻址落盘 = 幂等 CAS）
→ W = quorum(R) 个节点持久且校验通过（默认 W=quorum；R=2 可配 W=1 换可用性）
→ 返回确认集 C
```

部分写失败：未确认节点上的半截文件因校验不过自然作废；已确认节点上的完整
pack 若最终未注册，成为孤儿（GC 兜底）。

**读**：任一持有节点可服务（OID 即校验和 ⇒ 完整性自证，无需共识）；网关
pack cache 短路；整包直传语义保持。

**reconciler**（ref 服务主上单飞）：对账"索引登记的持有集 vs 实际持有"——
节点摘除 → 欠副本 pack 补齐到新随机节点 → 索引更新 → 旧节点清理；孤儿
pack 回收；节点磁盘损坏 → 从其余副本重灌。不可变数据使这些操作幂等无锁。

## 4. ref 服务（前序判断点）

- **职责**：refs/timelines 的 head CAS（push 前序判断 + fetch 广告）、对象
  索引（oid → (packOID, 持有节点集)）、仓库与放置记录；
- **写**：每 push 一个原子事务 `CommitPush{对象定位行 → (packOID, 确认集C),
  ref CAS}`——前序判断与注册同事务，崩溃窗口仅剩"pack 已落盘、未注册"
  的孤儿（无害）；
- **后端双选**：
  - **MySQL/PG（集群默认）**——前序判断走 DB 事务，HA 由数据库体系承担
    （企业现成 DBHA / 云 RDS 多 AZ）；
  - **内嵌 raft 组（自包含场景）**——不想引入外部 DB 时，ref 状态本身是
    小状态机（每 push 1-2 条命令），3 成员 raft 组即可（复用 raft 库，
    容 1 节点故障）；一体化模式退化为 SQLite 直调；
- **读**：refs/广告走主库强读；对象索引走异步只读副本，**未命中回主库**
  （兜住"push 后立即 fetch"）；网关另有一层定位缓存——对象位置只在 repack
  时变化，缓存命中率天然极高。

## 5. 写路径（push，全图）

```
① 网关解码 pack → packOID
② 随机/低负载选 R 个健康节点
③ 并行流式写 → W 确认 → 确认集 C
④ ref 服务：事务 CommitPush{objects→(packOID, C), ref 前序判断 + CAS}
⑤ report-status
```

网关扇出实现简单；HA-2 可演进为"写主节点 + 节点间扇出"降低网关出带宽。

## 6. 读路径（fetch/clone）

ref 广告（主库）→ 闭包与对象定位（只读副本，miss 回主库；网关定位缓存）→
pack 从**任一持有节点**流式获取（cache / 整包直传）。

## 7. 可用性语义

**ref 面**：取决于后端——MySQL/PG 按其 HA（通常多 AZ 自动切换）；内嵌 raft
3 成员容 1（选举 ~1s，窗口不可写，CP）。

**数据面**（per-repo R，W = quorum(R)）：

| R | 单节点故障时 |
|---|---|
| 1 | 该仓数据不可用（无冗余；冷仓/开发仓） |
| 2 | **已注册数据可读**（任一持有者）；新写默认阻塞（W=2）；可配 W=1 续写（明确牺牲：主节点盘毁且未补齐窗口内可能丢该 pack） |
| 3 | **读写皆续**（W=2）——平稳 HA |
| ≥5 | 容忍更多节点（奇数为宜） |

组件级故障：

| 故障 | 影响 | 恢复 |
|---|---|---|
| 网关实例宕 | 无感（LB 摘除） | 无动作 |
| ref 服务主宕 | 窗口内不可写（CP）；已提交事务零丢失（DB 复制 / raft） | 后端切换（秒级） |
| 存储节点宕 | 该节点持有的 pack：R≥2 从其余持有者读；新写不再选它 | reconciler 将欠副本 pack 补齐到其他节点 |
| 双存储节点同时宕 | 仅同时丢失同一 pack 全部副本才影响数据（R≥3 时概率极低）；索引可写 | 重灌或接受丢失并标记 |
| 磁盘损坏单节点 | 该节点 pack 失效 | reconciler 校验和重灌 |

## 8. 配置形态（banyan.yaml）

```yaml
role: all-in-one            # all-in-one（默认）| gateway | refs | storage
listen: 0.0.0.0:8080
root: /var/lib/banyan       # storage 角色：pack 数据
refs:                       # refs 角色
  backend: mysql            # mysql | postgres | raft | sqlite（一体化）
  dsn: "user:pass@host/db"
  read_replica_of: ""       # 只读副本填主地址
raft:                       # refs backend=raft 时
  node_id: r1
  peers: ["r1@h1:8101", "r2@h2:8101", "r3@h3:8101"]
gateway:
  refs: ["h1:8102"]         # ref 服务端点
  storage: ["s1:8103", "s2:8103", "s3:8103", ...]   # 健康表来源
placement:
  default_replicas: 3
  write_acks: quorum        # quorum | all | one（R=2 时的可用性旋钮）
```

内部端口（raft 8101 / ref 8102 / storage 8103）不对外；互信 v1 共享 token
（随 M5 认证升级 mTLS）。

## 9. 与现有代码的映射

| 现有构件 | 集群化后的去处 |
|---|---|
| `MetaStore` 接口 | 不变；集群实现 = ref 服务客户端（写=CommitPush 事务；读=主/副本路由） |
| `PickNodes`（rendezvous） | 输入改为健康节点表，策略改随机/最低负载（rendezvous 退场：登记即事实，无需放置函数） |
| `ObjectService.lookupPack`（本地盘） | 持有节点客户端（任一持有者取 pack） |
| `rpc/gitwire/service` 三层 | 整体成为网关角色（Gitaly 前端同挂网关） |
| 一体化部署 | refs 进程内 SQLite + storage 单节点；无特例路径 |
| repack（register-first） | 网关编排：读各持有节点包 → 合并包随机写 R 节点 → ref 事务 DropPack + 旧节点清理命令 |

## 10. 测试计划（docs/07 约定）

| # | 用例 | 防回归点 |
|---|---|---|
| T23 | push 后随机放置可读：确认集与索引一致，任一持有节点可服务 | 散布放置与登记事实一致 |
| T24 | 存储节点宕（R=3）：读写皆续；欠副本自动补齐；节点回归不冲突 | 故障转移与 reconciler |

## 11. 里程碑与风险

```
HA-1：三角色拆分 + 散布多副本写 + ref 服务（MySQL/PG 后端 + 只读副本）+ reconciler
HA-2：ref 内嵌 raft 后端、节点间扇出写、备份与恢复工具
HA-3：机架/可用区感知放置、跨集群异步复制（容灾）、S3 类对象存储后端
```

roadmap 对位：HA-1 吸收原 M2 的"ShardStore 远端 + rendezvous + R 副本"三项
（rendezvous 被"随机放置 + 登记即事实"取代）。

| 风险 | 缓解 |
|---|---|
| 复制协议正确性自研（部分写/校验/孤儿） | 内容寻址使一切幂等可验证；T23-T27 钉住；reconciler 各方案本就必需 |
| ref 服务后端单写吞吐 | 每 push 1 小事务，量级估算充裕；不足升 MySQL（接口不变） |
| 随机放置的长期倾斜 | 最低负载策略 + reconciler 再平衡钩子 |
| 只读副本/定位缓存滞后 | miss 回主库兜底；对象位置仅在 repack 变化，天然高命中 |
| raft 后端（可选）选主窗口 | ~1s 不可写（CP），与 git 客户端重试语义兼容 |
